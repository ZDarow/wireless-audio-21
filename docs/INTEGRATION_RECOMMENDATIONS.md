## 1. Приоритет 1 — Безопасность (критично для открытого проекта)

### 1.1 V4 — Аутентификация UDP-источника (мастер ← смартфон)

**Проблема:** Мастер принимает UDP-пакеты с магией `0xA210` без проверки источника. Любой в локальной сети может подделать аудиопоток.

**Решение:** Использовать существующую поддержку HMAC-SHA256 в `udp_audio_packet.h` (магия `0xA211`).

**Шаги интеграции:**
1. Добавить ключ `AUDIO_UDP_AUTH_KEY` в `config.env` / `generated_config.h` (минимум 32 символа)
2. В `master_s3/src/main.cpp` при получении пакета:
   - Если магия `0xA211` — проверять HMAC-SHA256 (первые 8 байт payload = HMAC)
   - Если магия `0xA210` и ключ настроен — отбрасывать с предупреждением
   - Если ключ не настроен — принимать `0xA210` с предупреждением в лог (обратная совместимость)
3. Добавить проверку `remoteIP` против доверенной подсети (опционально, §17 ТЗ)

**Сложность:** Низкая (1–2 дня)
**Риск:** Низкий
**Эффект:** Закрывает уязвимость V4

**Готовый код:** см. `docs/EXTERNAL_REFERENCES.md` §4.1

### 1.2 V5 — Подпись OTA-образа

**Проблема:** OTA через `Update.end(false)` проверяет только целостность. Нет подписи образа — можно загрузить прошивку злоумышленника.

**Вариант A (быстрый, рекомендуется для открытого проекта): SimpleOTA Ed25519**
- Подписывать бинарник в CI с приватным ключом Ed25519
- Проверять подпись на устройстве перед `Update.end()`
- Использовать Monocypher 3.1.3 (легкая библиотека, встроить в проект)
- Публичный ключ хранится в `generated_config.h` или NVS

**Вариант B (правильный, для продакшена): Secure Boot v2 (ESP-IDF)**
- RSA-3072 + RSA-PSS, ключ в eFuse
- Требует программирования eFuse (необратимо)
- Для личного проекта — избыточно на старте

**Шаги интеграции (Вариант A):**
1. Добавить Monocypher в `lib_deps` или скопировать исходники в `firmware/common/crypto/`
2. В CI: подписывать `firmware.bin` приватным ключом, загружать подпись как артефакт
3. На устройстве: в `handleUpdateUpload` проверять подпись перед пометкой образа bootable
4. Добавить эндпоинт `/api/ota/verify` для проверки подписи без прошивки

**Сложность:** Средняя (1–2 недели)
**Риск:** Средний (ошибка в проверке может заблокировать легитимные обновления)
**Эффект:** Закрывает уязвимость V5

**Готовый код:** см. `docs/EXTERNAL_REFERENCES.md` §4.2

### 1.3 S-1 — Дефолтный пароль AP

**Проблема:** Пароль AP `audio21master` попадает в каждую прошивку при отсутствии `config.env`.

**Решение:** При первом запуске, если пароль не изменён, блокировать Web UI до смены пароля (forced password change).

**Шаги:**
1. Добавить флаг `adminPasswordChanged` в NVS (версия v5)
2. При загрузке: если флаг не установлен — `/api/admin/setup` обязателен, остальные эндпоинты возвращают 403
3. Предупреждение в serial + Web UI баннер (уже есть)

**Сложность:** Низкая (1–2 дня)
**Риск:** Низкий
**Эффект:** Закрывает уязвимость S-1

## 2. Приоритет 2 — Синхронизация сателлитов (C3.4)

**Проблема:** `drift_correction.h` существует (медианный фильтр 8 отсчётов, host-тест зелёный), но не интегрирован в `satellite/src/main.cpp`. Без коррекции дрейфа каналы со временем рассинхронизируются — критично для стерео-сцены 2.1.

**Решение:** Интегрировать `DriftCorrector` в цикл сателлита.

**Шаги интеграции:**
1. В `satellite/src/main.cpp` создать `DriftCorrector g_driftCorrector;`
2. При приёме пакета: `g_driftCorrector.process(packet.renderTimestamp, millis())`
3. Корректировать `targetMs` в `JitterBuffer` на основе медианы
4. Добавить `startPlaybackAtMs` — все сателлиты начинают воспроизведение пакета с одинаковым абсолютным временем (PTP-подобная синхронизация, F19)
5. Логировать `drift_corrections` в `/api/status`

**Сложность:** Средняя (3–5 дней)
**Риск:** Средний (ошибка в коррекции может вызвать щелчки)
**Эффект:** Закрывает F14, F19, критично для стерео-синхронизации

**Готовый код:** см. `docs/EXTERNAL_REFERENCES.md` §4.3

## 3. Приоритет 3 — Архитектура и тестирование

### 3.1 Дekomпозиция web_server.h

**Проблема:** Монолит ~976 строк реализации + 430 строк SPA HTML. Сложно компилировать, невозможно переиспользовать SPA отдельно.

**Решение:** Разбить на модули.

**Шаги:**
1. Вынести `web_spa.h` HTML/CSS/JS в отдельные `.h` файлы с `PROGMEM` или в SPIFFS/LittleFS
2. Разделить `web_server.cpp` на: `web_auth.cpp`, `web_api.cpp`, `web_ota.cpp`, `web_wifi.cpp`, `web_logs.cpp`
3. Заменить `String` на `std::string` / `char[]` там, где возможно (снизить фрагментацию heap)
4. Сгруппировать 9 параметров конструктора в `struct AudioContext` (ISP, T16)

**Сложность:** Средняя (3–5 дней)
**Риск:** Низкий (рефакторинг без изменения функционала)
**Эффект:** Поддерживаемость, тестируемость

### 3.2 SSE endpoint для статуса сателлитов

**Проблема:** SPA опрашивает `/api/status` каждые 2 с — лишний трафик, задержка обновления.

**Решение:** Добавить Server-Sent Events endpoint `/api/events`.

**Шаги:**
1. Добавить `GET /api/events` в `web_server.h` — поток `text/event-stream`
2. Отправлять обновления при изменении статуса сателлитов, громкости, кроссовера
3. На клиенте: `new EventSource('/api/events')` вместо `setInterval(fetch, 2000)`

**Сложность:** Низкая (1–2 дня)
**Риск:** Низкий
**Эффект:** Уменьшение трафика, более отзывчивый UI

### 3.3 CI/CD активация и HIL

**Проблема:** GitHub Actions написан, но 0 runs (не активированы). Нет тестирования на реальном железе.

**Решение:**
1. Активировать GitHub Actions в настройках репозитория (Settings → Actions → Enable)
2. Добавить `pio test -e native` в workflow для хост-тестов
3. Рассмотреть self-hosted runner с реальным ESP32-S3 для HIL тестирования (flashing + serial валидация)
4. Закрепить `ArduinoJson` точной версией (не `^7.4.3`, а `7.4.3`)

**Сложность:** Низкая (активация) / Высокая (HIL runner)
**Риск:** Низкий
**Эффект:** Автоматическая проверка сборки и тестов на каждый PR

## 4. Приоритет 4 — Функциональные улучшения

### 4.1 Preset-менеджмент

**Проблема:** Нет способа сохранить/загрузить конфигурацию DSP (громкости, кроссовер, задержки).

**Решение:**
1. Добавить эндпоинты `POST /api/presets/save` и `POST /api/presets/load`
2. Сохранять в NVS с именами пресетов
3. Экспорт/импорт JSON через REST API

**Сложность:** Средняя (3–5 дней)
**Риск:** Низкий

### 4.2 Dirty indicator на ползунках Web UI

**Проблема:** Пользователь не видит, какие настройки изменены, но не сохранены.

**Решение:** Добавить визуальный индикатор на ползунках (изменённый цвет/точка) при расхождении UI-значения с сохранённым.

**Сложность:** Низкая (1–2 дня)
**Риск:** Низкий

### 4.3 mDNS (уже частично реализовано F16)

**Статус:** F16 помечен как ✅, но стоит проверить работоспособность на железе.

**Рекомендация:** Добавить проверку mDNS в ручное тестирование (§19).
